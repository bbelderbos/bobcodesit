# Python hides Unicode; Rust makes you face it

Paste 🙏 into a tweet and watch the character counter drop by two. That's not a bug — it's Unicode. The emoji lives at U+1F64F, outside the Basic Multilingual Plane, so platforms that count in UTF-16 units (Twitter) see a surrogate pair: two code units, not one.

Python 3 shields you from this. Strings are sequences of Unicode code points, so `len` gives you what you'd intuitively expect:

```python
>>> len("🙏")
1
>>> len("hello 🙏")
7
```

Rust does not shield you. `String` and `&str` are UTF-8 bytes, and `.len()` counts bytes:

```rust
fn main() {
    let s = "🙏";
    println!("{}", s.len());           // 4  — bytes in UTF-8
    println!("{}", s.chars().count()); // 1  — Unicode scalar values
}
```

That's why the JSON parser curriculum stores input as `Vec<char>` instead of `&str` — iterating `chars()` and indexing by position is far less surprising than slicing raw bytes (which will panic if you land mid-codepoint).

The practical rule: in Rust, always choose the right unit for the job.

| You want | Use |
|----------|-----|
| Byte length (network, I/O) | `.len()` |
| Displayed character count | `.chars().count()` |
| Grapheme clusters (visible glyphs) | `unicode-segmentation` crate |

If you're building anything that counts characters for a user — tweet composer, text field limit, progress bar — `.len()` will lie to you. Reach for `.chars().count()` at minimum, or the `unicode-segmentation` crate if you need to handle combined characters like `é` (e + combining accent = 1 visible glyph, 2 scalar values).

Python's abstraction is convenient right up until it isn't (try splitting a string by grapheme cluster in Python without a third-party lib). Rust just makes the tradeoffs visible from the start.
