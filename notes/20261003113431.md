# Deploy only after CI passes with workflow_run

Keep CI and deploy as separate workflows and chain them with `workflow_run`. The deploy fires when CI *completes* — pass or fail — so guard the job with an `if`.

```yaml
name: Deploy

on:
  workflow_run:
    workflows: [CI]        # matches the CI workflow's `name:`, not its filename
    types: [completed]
    branches: [main]

concurrency: deploy        # never run two deploys at once

jobs:
  deploy:
    # completed != succeeded, and skip PR-triggered CI runs
    if: github.event.workflow_run.conclusion == 'success' && github.event.workflow_run.event == 'push'
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
        with:
          ref: ${{ github.event.workflow_run.head_sha }}   # deploy the exact commit CI tested
      - uses: superfly/flyctl-actions/setup-flyctl@master
      - run: flyctl deploy --remote-only
        env:
          FLY_API_TOKEN: ${{ secrets.FLY_API_TOKEN }}
```

Gotchas: `workflow_run` only triggers from the default branch's copy of the file, and renaming CI silently breaks the chain. A single workflow with `needs: test` is simpler, but splitting lets you re-run a deploy on its own and keeps PRs away from deploy secrets.

Set the secret in one go: `fly tokens create deploy -a myapp | gh secret set FLY_API_TOKEN`
