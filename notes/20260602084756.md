# Don't reinvent the wheel — Rust's std already parses signed integers

Parsing a JSON-ish primitive, I first wrote a `parse_with_optional_sign` helper that peeked at the first char, stripped a leading `+`/`-`, parsed the rest, and re-applied the sign. A whole function to handle something the standard library already does.

Both `str::parse::<i64>()` and `i64::from_str_radix(s, 10)` accept an optional leading sign out of the box — `"+9"` and `"-7"` just work. So the helper was dead weight. The only thing worth keeping is the error *classification*: when parsing fails, `ParseIntError::kind()` returns an `IntErrorKind`, and the `PosOverflow` / `NegOverflow` variants let you tell "number too big" apart from "not a number at all".

```rust
use std::num::IntErrorKind;

fn parse_primitive(input: &str) -> Result<JsonValue, ParseError> {
    let s = input.trim();
    if s.is_empty() {
        return Err(ParseError::Empty);
    }
    match s {
        "true" => Ok(JsonValue::Bool(true)),
        "false" => Ok(JsonValue::Bool(false)),
        "null" => Ok(JsonValue::Null),
        // std handles the +/- sign; we just map the failure kind
        _ => match s.parse::<i64>() {
            Ok(n) => Ok(JsonValue::Number(n)),
            Err(e) => match e.kind() {
                IntErrorKind::PosOverflow | IntErrorKind::NegOverflow => Err(ParseError::Overflow),
                _ => Err(ParseError::Invalid),
            },
        },
    }
}
```

The lesson generalizes: before writing a parsing/string-munging helper, check whether `std` already covers it. The wheel here wasn't just reinvented — the std version handles edge cases (empty after sign, lone `+`) that the hand-rolled one would need extra branches for.
