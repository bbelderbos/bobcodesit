# Fail fast at startup: typed settings plus a dependency check

A missing env var or a dead database should crash your app on boot, not on the
first request an hour later. `pydantic-settings` gives you half of that for
free: declare the config as typed fields and `Settings()` raises a
`ValidationError` listing every missing or malformed value at once.

The other half is exercising the external services once at startup. It's
tempting to put the `ping()` inside a `field_validator`, but then every
`Settings()` call does network I/O — including in your unit tests. Keep the
settings pure and run the checks in one explicit startup step instead.

```python
import sys

import redis
from pydantic import PostgresDsn, RedisDsn, SecretStr
from pydantic_settings import BaseSettings, SettingsConfigDict
from sqlalchemy import create_engine, text


class Settings(BaseSettings):
    model_config = SettingsConfigDict(env_file=".env", extra="ignore")

    openai_api_key: SecretStr  # required, and hidden in reprs/logs
    database_url: PostgresDsn  # URL shape checked, not reachability
    redis_url: RedisDsn
    environment: str = "development"


def check_dependencies(settings: Settings) -> None:
    engine = create_engine(
        str(settings.database_url), connect_args={"connect_timeout": 3}
    )
    try:
        with engine.connect() as conn:
            conn.execute(text("SELECT 1"))
    finally:
        engine.dispose()

    with redis.Redis.from_url(
        str(settings.redis_url), socket_connect_timeout=3, socket_timeout=3
    ) as client:
        client.ping()


if __name__ == "__main__":
    try:
        settings = Settings()
        check_dependencies(settings)
    except Exception as e:
        sys.exit(f"❌ Startup failed:\n{e}")
    print("✅ Config valid, Postgres and Redis reachable")
```

In FastAPI, call `check_dependencies()` from the `lifespan` handler so a bad
deploy never starts serving traffic. In tests, build `Settings(...)` directly
with fake values — no network needed — and test the checker separately.

Valid config doesn't mean reachable services, and a clean boot doesn't mean
they stay up: this complements readiness/liveness probes, it doesn't replace
them.
