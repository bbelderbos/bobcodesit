# .copied() beats |&s| destructuring in Rust iterator chains

When you call `.iter()` on a slice you get references (`&T`). If `T` is `Copy` (like `u32`, `i64`, `bool`) and the next step wants an owned value, you've got two ways to bridge it:

```rust
// destructure the reference in the closure
scores.iter().map(|&s| bonus(s)).collect()

// or copy first, then pass the function by name
scores.iter().copied().map(bonus).collect()
```

Both compile to the exact same machine code. Zero-cost abstraction: `.copied()` is a thin adapter the optimizer inlines away. So it's a readability call, not a perf call.

The second form wins for me because:

- `.copied()` says "I want owned values" in plain English. `|&s|` makes the reader pause to parse a pattern.
- You can hand `map` a bare function reference instead of wrapping it in a closure. Closer to Python's `map(bonus, scores)`.
- Fewer moving parts when you chain more adapters after it.

For non-`Copy` types like `String`, use `.cloned()` instead — but be aware that's a real allocation, not free. For primitives, reach for `.copied()`.
