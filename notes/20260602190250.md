# Freeze the clock so date tests can't flake at midnight

A test that writes "today" and then asserts "today" looks deterministic but isn't. If the code under test calls `date.today()` once and the assertion calls it again, the two reads can disagree — the test straddles midnight, the file says June 2, the assertion computes June 3, and you get a flake once every few CI-years that nobody can reproduce.

The fix is to stop relying on the wall clock twice. `freezegun` pins `date.today()` (and `datetime.now()`) everywhere for the duration of the test, so both reads see the same frozen value and you can assert against a literal date.

```python
from datetime import date
from freezegun import freeze_time

# flaky: today() runs in the code AND in the assertion — they can differ
def test_add_note_dated():
    add_note("called back")
    assert date.today().isoformat() in last_note()

# stable: one frozen clock, assert the literal
@freeze_time("2026-06-02")
def test_add_note_dated():
    add_note("called back")
    assert "2026-06-02" in last_note()
```

Bonus: freezing also lets you tighten date-math tests you couldn't pin before. A `remind --in 7` command that computes `today + 7 days` is normally only checkable for "is the text there?" — with `@freeze_time("2026-06-02")` you can assert the due date is exactly `2026-06-09`.

Why `@freeze_time` over `@patch('datetime.date', ...)`: manual patching is brittle against import style. The moment the code switches from `import datetime` to `from datetime import date`, your patch target is wrong and the test breaks for reasons unrelated to the logic. freezegun fakes datetimes thoroughly enough that it doesn't care how the module imported them.

`uv add --dev freezegun`. Reach for it whenever a test's correctness depends on what day it runs.
