# Find the source of a ResourceWarning with PYTHONTRACEMALLOC

When Python prints `ResourceWarning: unclosed ...` it tells you *something* leaked but not *where it was allocated*. The warning itself nudges you: `Enable tracemalloc to get the object allocation traceback`. Flip one env var and the next run includes the full allocation stack.

```python
# leak.py - opens a file and walks away
import gc

def make_file():
    return open("/tmp/dummy.txt", "w")

f = make_file()  # never closed
del f
gc.collect()     # force collection while tracemalloc is still alive
```

Run it with tracemalloc on and warnings un-suppressed:

```bash
PYTHONTRACEMALLOC=20 python -W default leak.py
```

Output:

```
/tmp/leak.py:8: ResourceWarning: unclosed file <_io.TextIOWrapper name='/tmp/dummy.txt' mode='w' ...>
  del f
Object allocated at (most recent call last):
  File "/tmp/leak.py", lineno 7
    f = make_file()  # never closed
  File "/tmp/leak.py", lineno 5
    return open("/tmp/dummy.txt", "w")
```

Three pieces matter:

- `PYTHONTRACEMALLOC=20` retains the last 20 frames of allocation history for every tracked object. Off by default because it costs memory + CPU. Doesn't matter for a debug run.
- `-W default` re-enables warnings that pytest and some runners suppress. Without it, `ResourceWarning` is silent.
- The explicit `del f; gc.collect()` forces collection *before* interpreter shutdown. Without it the warning still fires, but tracemalloc is already torn down — you get the warning with no allocation trail. In pytest this happens naturally during test teardown, so the trace shows up without extra effort.

Note: not every stdlib type emits `ResourceWarning` on `__del__` — files, sockets, `subprocess.Popen`, and asyncio transports do; `sqlite3.Connection` does not. If you suspect a leak from a type that doesn't warn, wrap it in a context manager or audit the close path directly.

For pytest specifically:

```bash
PYTHONTRACEMALLOC=20 uv run pytest tests/ -W default
```

Read the traceback bottom-up: the deepest frame is where the resource was opened. Scan for the first frame in *your* code (skip `.venv/...`). That's almost always the bug site.

Bonus: once the leak is fixed, re-run with `-W error::ResourceWarning` to promote any future leak straight to a test failure.
